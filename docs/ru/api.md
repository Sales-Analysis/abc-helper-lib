# Соглашения API

На этой странице собраны общие правила реализации, которые действуют для всех
пакетов библиотеки.

## Публичные точки входа

- корневой facade: `analytics.New()`
- facade товарной аналитики: `svc.Inventory()`
- facade клиентской аналитики: `svc.Customer()`
- пакетные анализаторы: каждый пакет анализа экспортирует `Analyze(ctx, input)`

## Общая форма API

- каждый анализ принимает собственную `Input`-структуру;
- каждый анализ возвращает собственную `Output`-структуру и `error`;
- для товарных анализов предпочтительное поле коллекции во `Input` — `Items`;
- для клиентских анализов поле коллекции во `Input` — `Customers`;
- стандартное поле верхнего уровня в `Output` — `Results`;
- `abc.Input.Products` остается поддерживаемым legacy-алиасом, но для нового кода нужно использовать `abc.Input.Items`;
- большинство анализов stateless и безопасно вызываются через package-level
  функции;
- составные анализы вроде `ABC-XYZ` оркестрируют нижележащие пакеты, а не
  дублируют формулы внутри одного большого facade.

## Работа с Context

- все анализаторы принимают `context.Context`;
- текущие реализации в основном используют context для проверки отмены;
- если context отменен, анализатор возвращает ошибку context.

## Правила сортировки

- большинство результатов сортируются по главной бизнес-метрике по убыванию;
- при равенстве значений ties обычно разрешаются через исходный порядок входа
  благодаря stable sort;
- если анализатор переставляет результаты относительно входа, элементы
  результата должны сохранять `OriginalIndex`;
- классификационные анализы добавляют `Summary`, когда групповые counts или
  верхнеуровневые totals реально помогают интерпретации результата.

## Правила defaulting

- `ABC`: дефолтные пороги `80/95`;
- `XYZ`: дефолтные пороги коэффициента вариации `10/25`;
- `VED`: дефолтные пороги критичности `70/40`;
- `FSN`: дефолтные пороги активности `70/1`;
- `Safety Stock`: дефолтный `ServiceFactor = 1.65`;
- `Churn`: дефолтно `30` дней до at risk и `90` дней до churn;
- `HML` и `SDE`: если явные пороги не заданы, они выводятся из данных.

## Политика validation

- неверная конфигурация возвращает `error`;
- ошибки порядка thresholds теперь возвращают `error`, а не молча сбрасываются в defaults;
- auto-defaulting сохраняется только для действительно пропущенной опциональной конфигурации;
- для `HML` и `SDE` явный override порогов должен быть полным и корректно упорядоченным.
- составные анализы пробрасывают validation errors из нижележащих анализаторов.
- структурно невозможные bounded inputs теперь тоже возвращают `error`, например:
  отрицательные order counts, отрицательный lead time, invalid ratio-поля и
  невозможные соотношения cycle-метрик в service level.

## Матрица Поведения Validation

| Случай | Поведение | Комментарий |
| :--- | :--- | :--- |
| Опциональная конфигурация не передана | Default | Примеры: пороги `ABC`, пороги `XYZ`, `ServiceFactor` в `Safety Stock` |
| Значение threshold вне допустимого диапазона | `error` | Примеры: percent > `100`, отрицательный threshold, invalid ratio |
| Порядок thresholds некорректен | `error` | Примеры: `B <= A`, `Y <= X`, `ChurnDays <= AtRiskDays` |
| Явный override порогов неполный там, где требуется полный override | `error` | Применяется к `HML` и `SDE` |
| Bounded numeric input отрицателен | `error` | Примеры: отрицательное число заказов, lead time, отклонение спроса |
| Float-вход равен `NaN` или `Inf` | `error` | Общий validation layer режет non-finite значения |
| Межполевая bounded-связь невозможна | `error` | Примеры: `FulfilledUnits > DemandedUnits`, `StockoutCycles > TotalCycles` |
| Вход формулы неположителен, но структурно допустим | Производная метрика становится `0` | Примеры: вычисления `EOQ`, `Safety Stock`, `Reorder Point` |
| Коммерческий scalar-вход напрямую участвует в ранжировании или формуле | Обычно `error`, если значение отрицательное или non-finite | Примеры: `Pareto.Value`, денежные поля `GM/Contribution`, `RFM.MonetaryValue`, `CLV.Revenue` |
| Датасет пустой | Пустой результат | `Results` остается пустым, `Summary` при наличии остается нулевым |
| Timestamp отсутствует | Интерпретация по умолчанию | `RFM` считает его очень старым, `Churn` мапит в возраст churn-threshold |
| Timestamp находится в будущем | `error` | `RFM` и `Churn` отклоняют future `LastOrderAt` |
| Rate передан как ratio или percent там, где это поддерживается | Нормализация | `CLV` принимает и форму `0..1`, и форму `0..100` |

## Политика edge cases

- неположительные числовые входы обычно дают `0` в производных метриках вместо
  жесткой validation error;
- коммерческие scalar-поля, которые напрямую влияют на ранжирование или
  финансовые формулы, постепенно переводятся на strict-поведение:
  finite и `>= 0`;
- пустые наборы данных возвращают пустые результаты;
- отсутствующие даты могут интерпретироваться по умолчанию, а не отклоняться:
  `RFM` трактует отсутствие даты как очень старую recency,
  `Churn` трактует отсутствие даты как возраст churn-порога;
- future timestamps отклоняются там, где контракт анализа опирается на
  историческую recency, сейчас это `RFM` и `Churn`;
- некоторые rates принимают и ratio-форму (`0..1`), и percent-форму
  (`0..100`), если это имеет смысл, например в `CLV`.

## Форма Ошибок

- Текущий validation contract возвращает обычные значения `error`.
- Validation errors сейчас используют текстовый префикс `invalid input: ...`.
- Typed validation errors пока намеренно не включены в стабильный публичный API.
- Новым интеграциям лучше опираться на поведение анализаторов и документированные правила, а не на конкретные типы ошибок.

## Deprecated API

- `abc.New()` и `(*ABC).Calculate(...)` все еще доступны для обратной
  совместимости;
- для новых интеграций лучше использовать `abc.Analyze(...)` или
  root/inventory facade.
